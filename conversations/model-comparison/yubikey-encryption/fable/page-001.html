Your proposed architecture is sound and all the pieces exist — here's how I'd assemble it, including the multi-YubiKey key provisioning part you were unsure about, plus a few real-world caveats I confirmed while checking the current state of the ecosystem.

The overall shape

Switch from a mounted container (Veracrypt) to per-file OpenPGP encryption: each secret is a .gpg file encrypted to one encryption subkey. The same ciphertext files then work identically on WSL2, bare Linux, and Android — the only thing that differs per platform is how gpg reaches the YubiKey. The subkey lives on N YubiKeys and in an offline backup, so any of them (or the bare key) can decrypt.

One thing you give up vs. Veracrypt: filenames and file sizes are visible, and there are no hidden volumes. If filename metadata matters, encrypt a tarball (gpgtar or tar | gpg) instead of individual files.

Key generation and provisioning to multiple YubiKeys

This is the standard "offline master key" workflow (the drduh YubiKey guide is the canonical reference):

  1. On a trusted machine (ideally offline, and using a throwaway GNUPGHOME), generate a certify-only primary key, then add separate subkeys for Encrypt, Sign, and Authenticate. I'd use rsa4096 — it's the most-tested path through OpenKeychain, which matters since that app is in maintenance mode. (ed25519/cv25519 works with YubiKey 5 firmware ≥5.2.3 and is faster over NFC, but is the less-beaten path on Android.)
  2. Back up before touching any YubiKey: gpg --export-secret-keys --armor to offline media (this is your "bare" copy), plus gpg --export of the public key and a revocation certificate. The whole GNUPGHOME directory is also worth tarring up.
  3. Provision card #1: gpg --edit-key, key N to select each subkey, keytocard, save. Critical gotcha: keytocard + save moves the key — your local copy becomes a stub pointing at that card.
  4. Provision card #2..N: restore the backed-up GNUPGHOME (or re-import the exported secret keys into a fresh one) and repeat keytocard. Each card ends up with an identical subkey but its own PIN/admin PIN.
  5. For "bare" use later, just import the secret-key export into whatever keyring needs it.

One multi-card annoyance to know about: a gpg stub records the serial number of the last card it saw, and older gpg will prompt "insert card with serial X" when you present card Y. GnuPG ≥2.3 handles interchangeable cards much better; on 2.2 the fix when swapping cards is gpg-connect-agent "scd serialno" "learn --force" /bye.

Android: Termux + OpenKeychain + okc-agents

The bridge you're looking for is OkcAgent (pkg install okc-agents in Termux). It proxies crypto operations from the Termux shell to OpenKeychain, which in turn talks to the YubiKey over NFC or USB-C OTG:

  • okc-gpg -d ~/storage/sdcard/secrets/foo.gpg — decrypt; OpenKeychain pops up and asks you to tap/insert the YubiKey.
  • okc-ssh-agent — an ssh-agent backed by OpenKeychain, which is the nicer answer for SSH specifically (more below).

Setup notes:

  • Install Termux from F-Droid or GitHub (the Play Store build is a different, restricted variant), and import your public key into OpenKeychain, then use its "security token" flow so it associates the key with the card.
  • This is exactly why gpg inside Termux can't do the job directly: Android doesn't give Termux's scdaemon access to USB smartcards (termux-api #393), so OpenKeychain has to be the component that owns the token.
  • Don't use --throw-keyids/hidden recipients when encrypting — OpenKeychain can't figure out which token key to use for hidden-recipient messages.
  • Removable SD card: Termux can read shared storage after termux-setup-storage, but Android typically only allows it to write to the removable card inside its own Android/data directory. Reading the encrypted blobs is fine; just decrypt into Termux's private $HOME (or pipe straight into the consuming process) and clean up after.

Honest caveat on this stack's health: OpenKeychain has been in maintenance mode since 2021 (last release 6.0.4, Feb 2024) and OkcAgent is also low-activity — there are scattered reports of breakage on newer Android versions. It broadly still works, but prototype the full Android flow on your actual device before migrating off Veracrypt, and keep the bare-key export as your escape hatch.

WSL2

Two viable approaches; I'd recommend the first:

  1. Gpg4win on Windows owns the YubiKey; relay its sockets into WSL2. Install Gpg4win, verify gpg --card-status works in PowerShell, then use npiperelay.exe + socat inside WSL2 to forward the Windows gpg-agent's named pipes to Unix sockets at the paths WSL2's gpg expects (worked example gist, step-by-step guide). Advantages: no attach/detach dance, and the key works in Windows and WSL2 simultaneously. Note recent Gpg4win moved its socket directory from %APPDATA%\gnupg to %LOCALAPPDATA%\gnupg — most older guides have the old path.
  2. usbipd-win USB passthrough into WSL2 with pcscd/scdaemon running natively in Linux. Purer, but the device attaches exclusively to WSL2, and there's ongoing friction with attach/detach and udev inside WSL.

In WSL2 you keep only the public key and stubs (gpg --import pubkey.asc; gpg --card-status creates the stubs); decryption is just plain gpg -d.

SSH keys specifically: consider not storing them as files at all

Since you already have an Authenticate subkey on the YubiKey, the cleaner pattern for SSH is to use it directly rather than decrypting a file containing an SSH private key:

  • Desktop/WSL2: enable-ssh-support in gpg-agent.conf (or on Windows, Gpg4win's PuTTY/OpenSSH agent support relayed through the same npiperelay setup), and your YubiKey is the SSH key.
  • Android: okc-ssh-agent in Termux does the same via OpenKeychain.

Then the encrypted-file store is only needed for the secrets that genuinely must exist as plaintext for a moment (passwords, keys for systems that can't use the agent). For the password portion, look at pass — it's exactly this design (per-secret GPG files in a git-syncable tree) and works with the same key on both platforms, though its Android companion apps are in a similar low-maintenance state as OpenKeychain.

Suggested order of attack

  1. Generate the offline key, back it up, provision one YubiKey.
  2. Prove the Android path end-to-end (Termux + OpenKeychain + OkcAgent + your device's NFC/USB) — this is the fragile link.
  3. Set up the WSL2 relay.
  4. Provision the remaining YubiKeys from the backup, migrate data out of Veracrypt, and only then retire it.

Partially confirmed, with an important exception: you're right that okc-ssh-agent only serves keys that OpenKeychain knows about as OpenPGP keys — it cannot read OpenSSH private key files. But "existing RSA SSH key" and "GPG-provisioned key" are not disjoint sets. An RSA key is just an RSA keypair; OpenPGP and OpenSSH are only different packagings of it, so you can import an existing RSA SSH key into GPG as an authentication subkey and then move it onto the YubiKey. The public key doesn't change, so every authorized_keys entry that already trusts that key keeps working.

The flow (worked example, opensource.com writeup):

  1. Convert a copy of the key to PEM: ssh-keygen -p -m PEM -f /tmp/id_rsa (modern OpenSSH keys are in openssh-key-v1 format, which the next step can't read).
  2. Import it into GnuPG's private key store: pem2openpgp 'ssh key' < /tmp/id_rsa | gpg --import (pem2openpgp comes from the Monkeysphere project).
  3. gpg --expert --edit-key <your-key> → addkey → "Existing key", identified by its keygrip, with capabilities set to Authenticate only. It's now an auth subkey under your certify primary.
  4. keytocard it into the Authentication slot, same as any other subkey — YubiKeys explicitly support imported RSA keys (YubiKey 5 handles RSA 2048–4096).
  5. Sanity-check that gpg --export-ssh-key <keyid> matches your original .pub before deleting anything.

Once that's done, the key works through the exact same plumbing as the rest of your setup: gpg-agent SSH support on WSL2, okc-ssh-agent on Android, and it's covered by the same offline backup/multi-YubiKey provisioning story.

The real constraints, which may or may not bite you:

  • The OpenPGP applet has exactly one Authentication slot per card. One existing RSA key can live on-token per YubiKey via this route. If you must support several existing SSH identities simultaneously, only one gets this treatment; gpg-agent can serve additional auth subkeys from software (bare) copies on desktop, but on Android, OpenKeychain + token gets you the one.
  • For extra keys on the desktop only, there's a second hardware option: import them into the YubiKey's PIV applet (yubico-piv-tool, slot 9a plus the retired-key slots) and use SSH's PKCS#11 support. That doesn't help on Android — Termux can't reach the token, which is the whole reason OpenKeychain is in the loop.
  • There are scattered reports of imported (non-generated) keys misbehaving on the OpenPGP applet, so test the imported key end-to-end — including through OpenKeychain — before trusting it.

So the decrypt-the-file-out-of-band fallback is only required on Android for existing SSH keys beyond the first one (or for non-RSA/odd-size keys the applet won't accept). If you have one primary RSA identity plus a long tail of rarely-used ones, a reasonable split is: primary key on-token as the auth subkey, the tail kept in your encrypted file store and decrypted into Termux's $HOME on the rare occasions you need them.

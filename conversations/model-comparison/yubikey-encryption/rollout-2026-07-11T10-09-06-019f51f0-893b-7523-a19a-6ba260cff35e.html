Your proposed setup is workable, but I’d make one important architectural change: don’t decrypt an SSH private-key file merely so ssh can read it. Put a dedicated OpenPGP authentication subkey on the YubiKey and use it through an SSH agent. The private key then never exists in Termux or WSL. For passwords and other files, OpenPGP-encrypted files are reasonable, provided you manage decrypted temporary files carefully.

Recommended key design

Create one OpenPGP identity offline with: • A certification-only primary key, retained offline. • An encryption subkey for your encrypted files. • An authentication subkey for SSH. • Optionally, a signing subkey for Git, documents, and so forth. Copy the same subkeys onto each YubiKey. Preserve an encrypted offline backup of all private keys before provisioning any token. Conceptually: 
Offline backup
├── certification primary key
├── encryption subkey ──→ YubiKey 1, YubiKey 2
├── authentication subkey ──→ YubiKey 1, YubiKey 2
└── signing subkey ──→ YubiKey 1, YubiKey 2
An OpenPGP card has separate signature, encryption, and authentication slots. keytocard transfers a key into one of these slots and normally replaces the local key with a card reference; it is not an ordinary copy operation. Yubico therefore explicitly recommends making an offline backup first. [Yubico’s importing-key instructions](https://developers.yubico.com/PGP/Importing_keys.html) For widest interoperability with Android, WSL, older SSH installations, and multiple YubiKey generations, I would use RSA 3072. Modern curves can work, but RSA eliminates a fair number of version-compatibility variables.

Generate the keys offline

Do this from a temporary Linux installation or live image disconnected from the network. Use a temporary GNUPGHOME, not your everyday GnuPG directory. A suitable structure can be created with: 
export GNUPGHOME=/path/on/encrypted/offline/media/gnupg
mkdir -m 700 "$GNUPGHOME"

gpg --quick-generate-key \
    "Personal Vault <vault@example.invalid>" \
    rsa3072 cert 2y
Find the full fingerprint: 
gpg --list-secret-keys --with-subkey-fingerprint
Then add the subkeys, substituting the primary-key fingerprint: 
gpg --quick-add-key PRIMARY_FINGERPRINT rsa3072 encr 2y
gpg --quick-add-key PRIMARY_FINGERPRINT rsa3072 auth 2y
gpg --quick-add-key PRIMARY_FINGERPRINT rsa3072 sign 2y
Export at least: 
gpg --armor --export PRIMARY_FINGERPRINT > public.asc
gpg --armor --export-secret-keys PRIMARY_FINGERPRINT > secret-full.asc
gpg --armor --export-secret-subkeys PRIMARY_FINGERPRINT > secret-subkeys.asc
gpg --output revocation.asc --gen-revoke PRIMARY_FINGERPRINT
Protect the private export with a strong passphrase and place copies on encrypted media in separate physical locations. Test importing the backup into another temporary GnuPG directory before relying on it. The revocation certificate should also be offline. It lets you revoke the identity if both the tokens and backup are compromised.

Provision each YubiKey

Before loading keys: 1. Reset the OpenPGP application if the token was previously used. 2. Change both the user PIN and admin PIN. 3. Record the token’s serial number. 4. Consider enabling touch requirements for signing, authentication, and decryption through YubiKey Manager. For every YubiKey, start from a fresh temporary GnuPG directory and import secret-full.asc. Do not try to provision token 2 using the keyring left after provisioning token 1, because keytocard may already have replaced the private material with card stubs. Run: 
gpg --edit-key PRIMARY_FINGERPRINT
At the gpg> prompt: 
toggle
Select the encryption subkey with key N, run keytocard, and choose the encryption slot. Repeat for the authentication and signing subkeys, choosing their corresponding slots. I recommend leaving the certification primary key off the everyday YubiKeys. You only need it offline for adding/revoking subkeys, changing expiration dates, or modifying the identity. After each token, verify: 
gpg --card-status
gpg --list-secret-keys --with-keygrip
Then test encryption and decryption before provisioning the next token.

Encrypting files

Encryption only needs the public key: 
gpg --recipient PRIMARY_FINGERPRINT \
    --output secrets.tar.gpg \
    --encrypt secrets.tar
Decrypt using the encryption subkey on the inserted YubiKey: 
gpg --output secrets.tar --decrypt secrets.tar.gpg
For a directory, create a tar archive first. OpenPGP encrypts streams/files; it does not provide a mounted filesystem comparable to VeraCrypt. Important consequences: • Filenames outside the encrypted archive remain visible. • Decrypted files become ordinary plaintext files. • Secure deletion is generally unreliable on SSDs, SD cards, and flash storage. • Avoid decrypting plaintext back onto the removable SD card if possible. • Prefer pipes, RAM-backed storage, or short-lived application-private storage. For plaintext passwords, a password manager with a well-understood Android workflow may be safer and more convenient than repeatedly extracting an encrypted archive. OpenPGP is especially suitable for small, relatively static emergency files and configuration bundles.

SSH without an SSH private-key file

Your authentication subkey can serve as the SSH identity. Export its public SSH representation: 
gpg --export-ssh-key PRIMARY_FINGERPRINT
Put that output into the server’s ~/.ssh/authorized_keys. On desktop Linux or WSL, add this to ~/.gnupg/gpg-agent.conf: 
enable-ssh-support
Then restart the agent: 
gpgconf --kill gpg-agent
gpgconf --launch gpg-agent
Set the SSH socket in your shell: 
export SSH_AUTH_SOCK="$(gpgconf --list-dirs agent-ssh-socket)"
Test with: 
ssh-add -L
ssh -v user@host
Now SSH asks gpg-agent to have the YubiKey perform authentication; it never reads a private-key file.

WSL2

The most direct arrangement is to attach the physical YubiKey to WSL using usbipd-win. From an elevated PowerShell prompt, initially: 
winget install --interactive --exact dorssel.usbipd-win
usbipd list
usbipd bind --busid <BUSID>
With a WSL terminal open, attach it from ordinary PowerShell: 
usbipd attach --wsl --busid <BUSID>
Inside WSL: 
lsusb
gpg --card-status
When finished: 
usbipd detach --busid <BUSID>
While attached to WSL, the device is unavailable to Windows applications. Microsoft documents this path specifically for USB devices such as smart-card readers. [Microsoft’s WSL USB instructions](https://learn.microsoft.com/en-us/windows/wsl/connect-usb) Within the distribution, install the normal smart-card components—for Debian/Ubuntu, typically: 
sudo apt install gnupg scdaemon pcscd
Depending on USB permissions, you may need an appropriate udev rule or temporary elevated access. Avoid running your normal GnuPG keyring as root. An alternative is to use Gpg4win on Windows and forward its agent into WSL, but that involves socket relays and lifecycle management. Direct usbipd attachment is generally easier to understand and troubleshoot.

“Bare” software-key operation

Your secret-full.asc backup permits this. On a trusted machine: 
export GNUPGHOME=/trusted/private/location
mkdir -m 700 "$GNUPGHOME"
gpg --import secret-full.asc
That machine can then decrypt without a YubiKey. This necessarily weakens the hardware-token security boundary while the software key exists there. Treat it as recovery or controlled offline operation, not the default workflow. The clean policy is: • Public key: freely copied to every device. • Private subkeys: on each YubiKey. • Full private backup: encrypted and offline. • Certification key: used only in the offline maintenance environment. • No decrypted SSH private-key files at all. • Plaintext data decrypted only into short-lived, private storage.

A smoother setup is possible, and you likely don’t need plaintext SSH-key files even for your legacy hosts.

Legacy SSH keys: decrypt directly into ssh-agent

Your existing hosts do not need any changes if you retain their existing SSH private keys. Store each private key encrypted with your OpenPGP encryption subkey, then decrypt it directly into a conventional SSH agent: 
eval "$(ssh-agent -s)"
gpg --decrypt legacy_id_ed25519.gpg | ssh-add -
Verify and connect: 
ssh-add -l
ssh user@legacy-host
When finished: 
ssh-add -D
ssh-agent -k
This gives you: • The existing SSH public key and server configuration remain unchanged. • The YubiKey authorizes decryption of the old private key. • The plaintext private key exists in the agent’s memory, but is never written to storage. • Any SSH implementation capable of using ssh-agent works normally. The analogous Termux command would use OkcAgent’s limited GPG interface to decrypt into an ordinary Termux ssh-agent: 
eval "$(ssh-agent -s)"
okc-gpg --decrypt legacy_id_ed25519.gpg | ssh-add -
Test the exact okc-gpg invocation because it supports only a subset of GPG’s options. [OkcAgent documentation](https://github.com/DDoSolitary/OkcAgent) This is substantially better than decrypting into $HOME/.ssh. If you absolutely must create a file, put it in Termux’s private app directory—not shared storage or the SD card—and use chmod 600. Termux documents that its app-private directory is isolated from other apps, while shared storage is not. [Termux filesystem documentation](https://github.com/termux/termux-packages/wiki/Termux-file-system-layout) One subtle correction to my earlier answer: an OpenPGP authentication subkey exported for SSH does not require GPG support on the server. The server just sees an ordinary SSH key and signature. However, it is a different public key from your existing SSH keys, so you would still need to add it to every host. The decrypt-to-ssh-agent approach avoids that migration requirement.

Should you wait for FIDO2 SSH on Android?

I wouldn’t make your current design depend on it. FIDO2-backed OpenSSH keys are excellent: 
ssh-keygen -t ed25519-sk
or, where Ed25519 security keys are unavailable: 
ssh-keygen -t ecdsa-sk
They give you hardware-protected keys, user-presence checks, and optional PIN/user-verification. Recent upstream OpenSSH and current preview Win32 OpenSSH builds include libfido2; Windows support is clearly advancing. [Win32 OpenSSH releases](https://github.com/PowerShell/Win32-OpenSSH/releases) Android itself has FIDO2/passkey APIs, but that does not automatically make a YubiKey available to the OpenSSH binary running inside Termux. The missing piece is a reliable bridge among: • Termux/OpenSSH • Android USB or NFC APIs • The hardware token • OpenSSH’s security-key provider interface That may eventually become polished, but there isn’t a sufficiently established, portable Termux workflow that I would wait for today. FIDO SSH keys also require server-side support for the sk-ssh-ed25519@openssh.com or sk-ecdsa-sha2-nistp256@openssh.com algorithms, generally OpenSSH 8.2 or later. Thus they have more server compatibility constraints than a GPG authentication subkey exported as an ordinary RSA SSH key. My migration path would be: 1. Preserve legacy keys as OpenPGP-encrypted blobs loaded with ssh-add -. 2. Add your GPG authentication public key to hosts you can readily update. 3. Experiment with FIDO2 SSH on desktop/WSL. 4. Add FIDO credentials as an additional key rather than replacing working credentials. 5. Revisit Android once a maintained agent/provider has a clean Termux integration.

Native Windows GPG is probably the better desktop owner

Yes: install Gpg4win and let its native gpg-agent/scdaemon own the YubiKey. This avoids handing the entire USB device to WSL with usbipd. That produces a cleaner ownership model: 
Windows
├── Gpg4win / gpg-agent ──→ YubiKey OpenPGP
├── Yubico Authenticator ──→ YubiKey OATH/TOTP
└── WSL
    ├── calls Windows gpg.exe, or
    └── connects to a forwarded Windows agent socket
With usbipd, Microsoft notes that an attached device is unavailable to Windows until detached. That is exactly the conflict you identified. [Microsoft WSL USB documentation](https://learn.microsoft.com/en-us/windows/wsl/connect-usb)

Simplest option: call Windows gpg.exe from WSL

WSL can invoke Windows executables directly. After installing Gpg4win, something like this should work: 
"/mnt/c/Program Files (x86)/GnuPG/bin/gpg.exe" --card-status
The actual path may instead be under C:\Program Files\GnuPG\bin; locate it in PowerShell with: 
Get-Command gpg.exe
For streaming operations, Windows GPG can read and write through WSL’s pipes: 
"/mnt/c/Program Files (x86)/GnuPG/bin/gpg.exe" \
    --decrypt encrypted-key.gpg |
ssh-add -
You may need to pass an explicit Windows-readable path when GPG itself opens a file: 
winpath=$(wslpath -w "$PWD/encrypted-key.gpg")

"/mnt/c/Program Files (x86)/GnuPG/bin/gpg.exe" \
    --decrypt "$winpath" |
ssh-add -
This is the option I would try first. It has fewer moving parts than forwarding GPG sockets and keeps smart-card ownership on Windows.

Important filesystem qualification

Windows programs cannot ordinarily open files stored only inside arbitrary Linux paths by their Linux pathname. Either: • Pipe the content through standard input. • Convert paths with wslpath -w. • Keep encrypted files somewhere both environments can access. • Use the \\wsl$\Distribution\... representation if the application handles UNC paths correctly. Piping is usually the cleanest: 
cat secret.gpg |
"/mnt/c/Program Files (x86)/GnuPG/bin/gpg.exe" --decrypt |
ssh-add -
GPG may need options adjusted to interpret encrypted input from standard input, but the underlying interop works.

Using the native Windows agent from WSL

This is possible but less turnkey. Current GnuPG has Windows support for Win32 OpenSSH and Windows named pipes, including the --enable-win32-openssh-support facility documented in the GnuPG manual. [GnuPG manual](https://www.gnupg.org/documentation/manuals/gnupg.pdf) There are two layers: 1. Windows Gpg4win’s gpg-agent talks to the YubiKey. 2. A bridge exposes its SSH-agent or GPG-agent endpoint as a Unix socket inside WSL. Community tools such as wsl2-ssh-pageant have historically provided this bridge, but these integrations are sensitive to Gpg4win versions, socket locations, WSL behavior, and the difference between GPG-agent and SSH-agent protocols. Microsoft still tracks native exposure of the Windows SSH agent inside WSL as a requested capability rather than a universally transparent built-in feature. [WSL agent integration discussion](https://github.com/microsoft/WSL/issues/11207) Therefore I’d use these approaches in this order: 1. Call native Windows gpg.exe from WSL. 2. For ordinary SSH keys, decrypt through Windows GPG into a WSL ssh-agent. 3. For routine GPG-backed SSH, consider running Windows ssh.exe with the Windows GPG agent. 4. Add an agent-socket bridge only if you specifically need Linux ssh to access the Windows GPG authentication subkey.

Yubico Authenticator coexistence

Keeping the token attached to Windows is much better than USB/IP for this purpose. Gpg4win and Yubico Authenticator address different YubiKey applications—OpenPGP and OATH—but they may still contend temporarily for smart-card/CCID access. You should expect occasional cases where you need to: 
gpgconf.exe --kill scdaemon
or close/reopen Yubico Authenticator. That is still far less disruptive than detaching the whole token from Windows and attaching it to WSL. My practical recommendation is therefore: • Gpg4win is the exclusive desktop owner of the OpenPGP card. • WSL calls Windows gpg.exe for encryption/decryption. • Legacy SSH keys are decrypted into a short-lived WSL ssh-agent. • GPG authentication subkeys are your preferred identity on newly provisioned hosts. • FIDO2 SSH is introduced opportunistically, without waiting for Android support.

Legacy SSH keys: decrypt directly into ssh-agent

Your existing hosts do not need any changes if you retain their existing SSH private keys. Store each private key encrypted with your OpenPGP encryption subkey, then decrypt it directly into a conventional SSH agent: 
eval "$(ssh-agent -s)"
gpg --decrypt legacy_id_ed25519.gpg | ssh-add -
Verify and connect: 
ssh-add -l
ssh user@legacy-host
When finished: 
ssh-add -D
ssh-agent -k
This gives you: • The existing SSH public key and server configuration remain unchanged. • The YubiKey authorizes decryption of the old private key. • The plaintext private key exists in the agent’s memory, but is never written to storage. • Any SSH implementation capable of using ssh-agent works normally. The analogous Termux command would use OkcAgent’s limited GPG interface to decrypt into an ordinary Termux ssh-agent: 
eval "$(ssh-agent -s)"
okc-gpg --decrypt legacy_id_ed25519.gpg | ssh-add -
Test the exact okc-gpg invocation because it supports only a subset of GPG’s options. [OkcAgent documentation](https://github.com/DDoSolitary/OkcAgent) This is substantially better than decrypting into $HOME/.ssh. If you absolutely must create a file, put it in Termux’s private app directory—not shared storage or the SD card—and use chmod 600. Termux documents that its app-private directory is isolated from other apps, while shared storage is not. [Termux filesystem documentation](https://github.com/termux/termux-packages/wiki/Termux-file-system-layout) One subtle correction to my earlier answer: an OpenPGP authentication subkey exported for SSH does not require GPG support on the server. The server just sees an ordinary SSH key and signature. However, it is a different public key from your existing SSH keys, so you would still need to add it to every host. The decrypt-to-ssh-agent approach avoids that migration requirement.

Should you wait for FIDO2 SSH on Android?

I wouldn’t make your current design depend on it. FIDO2-backed OpenSSH keys are excellent: 
ssh-keygen -t ed25519-sk
or, where Ed25519 security keys are unavailable: 
ssh-keygen -t ecdsa-sk
They give you hardware-protected keys, user-presence checks, and optional PIN/user-verification. Recent upstream OpenSSH and current preview Win32 OpenSSH builds include libfido2; Windows support is clearly advancing. [Win32 OpenSSH releases](https://github.com/PowerShell/Win32-OpenSSH/releases) Android itself has FIDO2/passkey APIs, but that does not automatically make a YubiKey available to the OpenSSH binary running inside Termux. The missing piece is a reliable bridge among: • Termux/OpenSSH • Android USB or NFC APIs • The hardware token • OpenSSH’s security-key provider interface That may eventually become polished, but there isn’t a sufficiently established, portable Termux workflow that I would wait for today. FIDO SSH keys also require server-side support for the sk-ssh-ed25519@openssh.com or sk-ecdsa-sha2-nistp256@openssh.com algorithms, generally OpenSSH 8.2 or later. Thus they have more server compatibility constraints than a GPG authentication subkey exported as an ordinary RSA SSH key. My migration path would be: 1. Preserve legacy keys as OpenPGP-encrypted blobs loaded with ssh-add -. 2. Add your GPG authentication public key to hosts you can readily update. 3. Experiment with FIDO2 SSH on desktop/WSL. 4. Add FIDO credentials as an additional key rather than replacing working credentials. 5. Revisit Android once a maintained agent/provider has a clean Termux integration.

Native Windows GPG is probably the better desktop owner

Yes: install Gpg4win and let its native gpg-agent/scdaemon own the YubiKey. This avoids handing the entire USB device to WSL with usbipd. That produces a cleaner ownership model: 
Windows
├── Gpg4win / gpg-agent ──→ YubiKey OpenPGP
├── Yubico Authenticator ──→ YubiKey OATH/TOTP
└── WSL
    ├── calls Windows gpg.exe, or
    └── connects to a forwarded Windows agent socket
With usbipd, Microsoft notes that an attached device is unavailable to Windows until detached. That is exactly the conflict you identified. [Microsoft WSL USB documentation](https://learn.microsoft.com/en-us/windows/wsl/connect-usb)

Simplest option: call Windows gpg.exe from WSL

WSL can invoke Windows executables directly. After installing Gpg4win, something like this should work: 
"/mnt/c/Program Files (x86)/GnuPG/bin/gpg.exe" --card-status
The actual path may instead be under C:\Program Files\GnuPG\bin; locate it in PowerShell with: 
Get-Command gpg.exe
For streaming operations, Windows GPG can read and write through WSL’s pipes: 
"/mnt/c/Program Files (x86)/GnuPG/bin/gpg.exe" \
    --decrypt encrypted-key.gpg |
ssh-add -
You may need to pass an explicit Windows-readable path when GPG itself opens a file: 
winpath=$(wslpath -w "$PWD/encrypted-key.gpg")

"/mnt/c/Program Files (x86)/GnuPG/bin/gpg.exe" \
    --decrypt "$winpath" |
ssh-add -
This is the option I would try first. It has fewer moving parts than forwarding GPG sockets and keeps smart-card ownership on Windows.

Important filesystem qualification

Windows programs cannot ordinarily open files stored only inside arbitrary Linux paths by their Linux pathname. Either: • Pipe the content through standard input. • Convert paths with wslpath -w. • Keep encrypted files somewhere both environments can access. • Use the \\wsl$\Distribution\... representation if the application handles UNC paths correctly. Piping is usually the cleanest: 
cat secret.gpg |
"/mnt/c/Program Files (x86)/GnuPG/bin/gpg.exe" --decrypt |
ssh-add -
GPG may need options adjusted to interpret encrypted input from standard input, but the underlying interop works.
